## Correctness & Unit-Tests

### ✅ C1. A linger flush that fails on a full buffer is never retried (reproduced)

`flushIfLingerElapsed` (469-480) calls `tryFlushAssumingLocked` once and ignores a `false`
result. Nothing reschedules it: `append` only calls `rescheduleFlushAssumeLocked` when the
current batch is empty or after a successful flush (360-369, 397), and the completion
callback (529-549) frees buffer space without looking at `currentBatch`. So once the linger
timer fires while the buffer is full, the current batch is sent only when a later `append`
finds it full, or at shutdown.

Consequence: after a backend outage or slowdown, the last (partial or full) batch stays in
memory for as long as the application is quiet, contradicting the `lingerMs` contract
("Max time to wait before sending a batch").

Repro: `lingerMs=200`, `maxBatchLogEvents=2`, `maxConcurrentRequests=1`,
`maxBatchBufferBatches=1`, WireMock answering after 1.5 s. Log `a1 a2 b1`, wait 50 ms, log
`b2 c1`. Batch A is in flight, B is buffered, `c1` lingers. After 8 s (40 x `lingerMs`) only
2 batches / 4 of 5 events have been delivered; `c1` is never sent.

Suggested fix: in the completion callback, while holding the lock, flush `currentBatch` if
its linger time has elapsed; alternatively let `flushIfLingerElapsed` reschedule itself when
the flush fails.

Resolved: a failed linger flush now sets `lingerFlushPending`, and the flush is retried when
the drain dequeues a batch and when a request completes. The reproducer is enabled (with
shorter timings than described above).

### ✅ C2. `BatchCompletionListener` implementations outside the package cannot read the HTTP status (reproduced)

`BatchDeliveredSuccess` and `BatchDeliveredError` (128-130) are public records with a
component of type `HttpStatus`, but `HttpStatus` is package-private (`HttpStatus.java:22`).
A listener in user code therefore fails to compile:

```java
if (event.type() instanceof AsyncHttpAppender.BatchDeliveredError error) {
    int code = error.httpStatus().code();
    // error: HttpStatus.code() is defined in an inaccessible class or interface
}
```

All existing listener tests live in the `appenders` package, which is why this went
unnoticed. Fix: make `HttpStatus` public (and consider the same for `RetryStats`, which is
only reachable through copied fields today).

Resolved: `HttpStatus` is now public. The reproducer is enabled and was generalised: it
walks the record components and sealed subtypes reachable from `BatchCompletionEvent` and
asserts that each type, including its enclosing classes, is public.

### ✅ C3. Buffered batches wait for a polling timer although a request slot is free (reproduced)

When `allowedInFlight` has no permit, `drainBufferedBatches` reschedules itself with a
random backoff that doubles up to 5 s (`maxDrainBufferBackoffNs1`, 210, 515-520). The
completion callback releases the permit (530) but does not trigger a drain, so the next
batch waits for whichever poll happens to fire next.

Repro: `maxConcurrentRequests=1`, `maxBatchLogEvents=1`, WireMock answering after 3 s, log
three events. Measured idle time between a response and the next request, over three runs:
369/676 ms, 1457/656 ms, 965/94 ms. The gap grows with request latency (bounded by 5 s),
so throughput drops exactly when the backend is slow and the buffer is filling up.

Suggested fix: call `drainBufferedBatches(maxDrainBufferBackoffNs0)` from the completion
callback (it already runs on the scheduler thread); the polling chain can then go away.
This also gives C1 a natural place for its fix.

Resolved: the completion callback now schedules a drain on the executor (not a direct call,
to avoid recursion when `sendBatch` fails synchronously), and the polling chain is gone. The
reproducer is enabled but was rewritten, since a 3 s delay is too slow for the regular test
run and shorter absolute timings proved flaky: it now asserts that a burst of 30 buffered
events takes less than 1.2 times as long as the same events sent one at a time (1 ms
response delay, best of 3 attempts after a warm-up round). Measured ratios were about 1.0
with the fix and 1.3 to 1.9 without.

## Security

### ✅ S1. An invalid header value, such as an API token, ends up in the status log (reproduced)

`sendBatch` passes each `Property` value to `HttpRequest.Builder.header` (589-591). For a
value with an illegal character the JDK throws
`IllegalArgumentException: invalid header value: "<value>"`. The exception becomes a
`BatchDeliveryFailed` event, and the default listener logs it at WARN, including the
exception, to the `StatusLogger` (1059), which prints to stderr by default. This repeats
for every batch.

Repro: add an `Authorization` property with the value `"Api-Token s3cr3t-token-value\n"`
via `ConfigurationBuilder.newProperty` (a trailing newline is typical for secrets read from
files or injected through lookups) and log one event: the status log contains the full token.

Suggested fix: build and validate the headers once per request in a `try` block and rethrow
with a message that names the header but not its value; ideally also validate static
headers at appender start.

Resolved: `sendBatch` now catches the `IllegalArgumentException` and rethrows one that names
the header but carries neither its value nor the original exception. The reproducer is
enabled and also asserts that the header name is reported. Validating static headers at
appender start was considered and left out as not worth the added complexity.

### ⬜ S2. The HTTP response body is buffered without limit and logged in full (reproduced)

`sendBatch` uses `BodyHandlers.ofString()` (597) and stores the whole body in
`HttpStatus.message`. The default listener prints it at INFO on success and at WARN on
error (1057-1061). A backend, proxy or captive portal that returns a large body makes the
single scheduler thread buffer it per request (5 MB body: 5,000,000 chars retained and
handed to the listener), and whatever it returns is copied verbatim into the status log,
or into application logs when `logBatchCompletionEvent` is used with a normal logger.

Suggested fix: cap the retained body (a few KB is plenty for diagnostics) and discard the
rest; consider discarding it entirely for success responses.

### ✅ S3. GitHub Actions are referenced by mutable tags

`.github/workflows/maven.yml` uses `actions/checkout@v7`, `actions/setup-java@v6` and the
third-party `dorny/test-reporter@v3`, which runs with `checks: write`. The workflow
permissions are already minimal and it does not use `pull_request_target`, so the risk is
low; pinning to commit SHAs (Dependabot's `github-actions` ecosystem keeps them current)
closes the remaining gap.

No hard-coded credentials were found in tracked files; redirects are not followed
(JDK default), and class names loaded reflectively come only from the trusted configuration.

## Code Readability

### ⬜ R1. Batch size is tracked twice, with two implementations of the separator rule

The size of the current batch is maintained incrementally in `currentBatchBytes` using
`needSeparatorAssumeLocked` (444-458) and then recomputed from scratch in
`calculateBatchSize` (860-875) using `isSeparatorNeeded` (1019-1024). The reader has to
prove that both agree, and `currentBatchBytes == 0` additionally serves as "batch is empty"
(373, 388, 445, 774).

They do not always agree (reproduced): with the default empty `batchPrefix`, an event that
serialises to zero bytes (e.g. `log.info("")` with pattern `%msg`) leaves
`currentBatchBytes` at 0, so the separator before the next event is not counted. With
`maxBatchBytes=3`, `batchSeparatorInsertionStrategy=always`, logging `""` then `"abc"`
yields one 4-byte batch. JaCoCo shows the relevant branch (446) is never executed by the
test suite. Impact is small (overshoot by one separator; from reading the code, a batch of
only empty events is also not counted by `hasUnpublishedLogData`), but it breaks the "exact accounting" invariant
stated in `CLAUDE.md`.

Suggestion: keep one predicate (`isSeparatorNeeded(prev, next)`), use
`currentBatch.isEmpty()` for emptiness, and either drop `calculateBatchSize` in favour of
`currentBatchBytes + batchSuffix.length` or assert that the two are equal.

### ⬜ R2. `append()` is 70 lines, four levels deep, and repeats its core block

Lines 373-380 and 388-395 are the same "account for prefix or separator, add event" block.
Extracting `addToCurrentBatchAssumeLocked(eventBytes)` and a
`blockUntilAppendedAssumeLocked(eventBytes)` helper for the overflow loop would reduce
`append` to the decision logic, and give R1's fix a single home.

### ⬜ R3. Smaller items

- `drainBufferedBatches` (507-581) nests a 50-line completion callback inside a loop inside
  a lambda; permit handling, lock bookkeeping, result classification and listener
  invocation are interleaved. Extracting `onBatchCompleted(...)` and a
  `toCompletionType(...)` helper would make the locking scope obvious.
- Lock-convention suffixes are inconsistent (`needsFlushAssumeLocked` vs
  `tryFlushAssumingLocked`), and some methods that require the lock have no suffix
  (`calculateBatchSize`, `processPotentialThrowable`, `completeInternal`).
- Names such as `maxDrainBufferBackoffNs0` / `Ns1` and `maxBatchBufferBytes0` do not say
  what they mean (initial vs. upper bound; base allowance).
- `AsyncHttpAppenderTest` is 2,098 lines covering config parsing, batching, retries,
  overflow, TLS and shutdown; splitting it by topic with a shared WireMock base class would
  make gaps like T1 and T3 easier to spot.

## Test Coverage

### ⬜ T1. `appendShouldInterruptThreadAfterCatchingInterruptedException` cannot fail (reproduced)

`AsyncHttpAppenderTest.java:1702-1737`. The only assertion runs on the helper thread, where
an `AssertionError` is lost; `join(200)` is not checked; and the logging loop also exits
normally when the interrupt arrives outside `awaitNanos`. In the baseline run JaCoCo shows
the `catch (InterruptedException)` block (408-411) as not executed at all. Replacing that
block with `throw new IllegalStateException(...)` (which drops the interrupt flag) still
gives a passing test in 3 of 3 runs, in two of which the mutated line was demonstrably hit.

Suggested fix: use `maxBlockOnOverflowMs=-1`, wait until the helper thread is parked in
`append`, interrupt it, hand the observed interrupt flag back (e.g. via a
`CompletableFuture`) and assert on the test thread.

### ⬜ T2. The `junit` module's only test asserts nothing and depends on the environment

`AsyncHttpAppenderFlushingTestExecutionListenerTest` logs one line and has no assertion;
its `log4j2-test.xml` points the appender at `${env:DYNATRACE_API_V2_LOGS_INGEST}`.

- Without the variable (CI), the appender fails to initialise ("Unable to invoke factory
  method ... AsyncHttp"), so the listener is only exercised with zero appenders.
- With the variable set (a developer machine), every `./mvnw package` sends a log line to
  the real Dynatrace tenant.

Either way a listener that never flushes would pass. Suggested fix: point the appender at a
WireMock server with a long `lingerMs` and verify, e.g. from a second
`TestExecutionListener` or a launcher-based test, that the request arrives when
`testPlanExecutionFinished` runs; also cover the `Enabled=false` switch (line 79 is
uncovered) and the timeout path.

### ⬜ T3. Scenarios without a test

Line coverage is high, so the gaps are behavioural rather than structural:

- Overload followed by recovery with no further traffic (C1), and time-to-next-request once
  a slot frees up (C3). Existing overload tests keep logging or shut down, which masks both.
- A `BatchCompletionListener` compiled outside the `appenders` package (C2).
- Zero-length events (R1) and oversized or secret-bearing inputs on the HTTP path (S1, S2).

A PIT run over the filters, `LogCaptor`, `LoggerNameUtil`, `HttpRetryManager`, `HttpHelpers`
and `CapturingAppender` killed 160 of 181 mutants (test strength 90%); `AsyncHttpAppender`
was left out because of its run time. `LogCaptor`, `ConstantFilter` and `CapturingAppender`
have no survivors. The survivors worth a test:

- `ThrottlingFilter.java:189-190`: both subtractions in the interval roll-over can be
  turned into additions without any test failing, so the alignment of a new interval after
  an idle period is unverified. Lines 161-162 (default `onMatch` / `onMismatch`) also survive.
- `RoutingFilter.java:172-204`: 9 survivors plus 1 uncovered in `start`/`stop`. The filter's
  own lifecycle state, the return value of `stop`, and the non-`LifeCycle2` branch of
  `stopFilter` are never asserted (`childFiltersShouldBeStartedAndStopped` only checks the
  children).
- `LoggerNameUtil.java:34-36`: the `null` branches are not covered.
